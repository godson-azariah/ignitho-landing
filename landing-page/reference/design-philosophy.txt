IGNITHO AI — DESIGN SYSTEM & PHILOSOPHY REFERENCE
====================================================
Purpose of this file: a portable description of the VISUAL DESIGN LANGUAGE used on this
site (colors, type, spacing, components, motion, responsive rules). It intentionally
excludes page copy/content — use it to make an AI or design tool replicate the LOOK AND
FEEL on a different page or project, not to recreate this specific site.

Tech context (for compatibility, not required): React + Tailwind, with hand-written CSS
for anything Tailwind cannot express cleanly. NO animation library — every animation
described in section 7 is plain CSS, and JavaScript only toggles a class or changes a
`key`. Any stack can replicate this system as long as it can produce the same CSS.

READ THIS BEFORE TRUSTING A SECTION: sections 4 (layout, spacing, placement, gaps) and
7 (motion and animation) were rewritten against the current build and are accurate.
The remaining sections describe an earlier iteration of the same brand — the colour
family, the type rules and the punctuation law still hold; specific component recipes
in section 6 do not all exist in this form any more.

ONE CASCADE WARNING that applies everywhere: if Tailwind is loaded as a runtime CDN
build, its utilities are injected into <head> BEFORE any bundled stylesheet, so a
hand-written class OVERRIDES a utility at equal specificity. A hand-written class must
therefore never declare a property a utility is also expected to set on the same
element. Two real failures from this: a class declaring `box-shadow` silently killed
Tailwind's `ring-1` (which compiles to box-shadow), and a class declaring
`position: relative` beat an `absolute` utility, collapsing a background layer to zero
height.


1. DESIGN PHILOSOPHY (the "why" behind the choices)
----------------------------------------------------
- "Enterprise-premium, not corporate-boring." Dark, saturated violet→teal gradients are
  used for high-impact moments (hero, CTA, dark feature cards) instead of flat corporate
  blue/white. The goal is to feel like a confident, modern AI product, not a generic
  SaaS brochure.
- "Bold color-blocked cards over tables/lists." Whenever content could be shown as a
  plain list, checklist, or comparison table, prefer a solid-gradient card treatment
  with icon badges instead — tables and plain bullet lists were explicitly rejected
  during design review as "too generic." Take inspiration from real premium component
  patterns (shadcn/ui, Aceternity UI, pricing-card layouts) rather than inventing
  arbitrary custom layouts from scratch.
- "Texture over flatness, but quiet." Every section background carries a very subtle
  dot-grid or line-grid texture (1–2px, low opacity) rather than being pure flat color.
  It should read as "premium paper texture," never as a distracting pattern — opacity
  stays under ~0.2 always.
- "Two-tone headline pattern." Nearly every section headline is two lines: the first
  line in the neutral near-black text color, the second line in the brand purple accent
  color. This is a consistent, repeatable rhythm across the whole site, not a one-off.
  Section headline copy is always followed by a purple-accent supporting paragraph.
- "Motion is a statement about attention, not decoration." Things ARRIVE (a one-shot
  reveal as a section is scrolled to, a blur-to-solid entrance inside an illustration)
  and things REPORT (a countdown ring, a fill that follows the pointer). Nothing loops
  in the reader's field of view, and the controls themselves — buttons, the navbar —
  hold perfectly still. Full detail in section 7, which is deliberately separable from
  the layout rules in section 4.
- "Never hide functionality behind a breakpoint." If content is important on desktop
  (navigation links, a hero visual, a key illustration), it must have an adapted mobile
  equivalent — resized, restacked, or moved into a menu — never just `display:none` with
  nothing to replace it.
- "Consistent horizontal rhythm." Every section shares the same content max-width and
  the same left/right padding, so edges line up perfectly as the user scrolls, on every
  viewport width. Avoid nested max-width containers that can drift out of alignment on
  very wide screens.
- "No trailing full stops, anywhere." No piece of copy on the site ends with a period —
  not headlines, not card descriptions, not metric/ROI values, not footer text, not
  chatbot messages, not helper captions. This is a deliberate house-style rule, applied
  site-wide with zero exceptions (including short punchy hero lines that "look like"
  complete sentences). See section 3 for the exact punctuation rule and what stays
  untouched (mid-paragraph sentence separators, true ellipses).


2. COLOR SYSTEM
----------------------------------------------------

"solution" framing, active/online states):
  --color-ignitho-teal:         #00A274   (base — primary buttons, active links, accents)
  --color-ignitho-teal-hover:   #0C8C74   (hover state for teal buttons)
  --color-ignitho-teal-border:  #00BC6A   (border ring on teal buttons, brighter lime-teal)

Secondary brand / depth color — VIOLET / PURPLE (used for dark gradient surfaces, and as
the accent color for the second line of every two-tone headline):
  Headline/body accent purple:   #7A00C2  (text-only accent, not used as a fill)
  --color-ignitho-violet-950:    #16063A  (darkest — gradient anchor, near-black-violet)
  --color-ignitho-violet-800:    #2C0A78
  --color-ignitho-violet-600:    #4A12B8
  --color-ignitho-violet-500:    #5B16C4  (brightest violet — gradient highlight stop)
  --color-ignitho-purple-600:    #3D08B8  (secondary "problem card" gradient stop)
  --color-ignitho-purple-700:    #5008D0

Deep teal-blue gradient stops (used at the tail end of the hero/CTA gradient, to bridge
violet into a cooler tone):
  --color-ignitho-teal-deep:     #123E68
  --color-ignitho-teal-deepest:  #0A5670

Secondary "fix / positive outcome" gradient family (green-teal, used opposite the violet
"problem" gradient in side-by-side comparisons):
  --color-ignitho-green-950:     #043620
  --color-ignitho-green-600:     #07924F
  --color-ignitho-green-500:     #0D8E92

Neutrals:
  --color-ignitho-text:          #030303  (headings/body — near-black, not pure black)
  --color-ignitho-muted:         #54595F  (secondary/caption text)
  --color-ignitho-divider:       #B9BBC2  (hairline borders/dividers)
  Card borders on white cards typically use Tailwind slate-200 (#E2E8F0).

Sparing accent:
  --color-ignitho-accent-blue:   #6EC1E4  (used only for small tech/status details — the
                                  chatbot "online" dot, one hero headline word — never as
                                  a large fill; a light sky-blue that reads as "signal/AI".)

Color usage rules:
  - Teal = action / positive / "the fix". Used for every primary button, every link
    hover state, checkmarks, and anything meant to read as "the good outcome."
  - Violet/purple = brand depth / premium / "the problem" or dark surfaces. Even negative
    framing (a "problem" card) stays inside the brand's violet family rather than
    switching to red/orange — the palette never uses alarm colors.
  - White/near-white with a faint tinted texture = default content background. Two
    interchangeable flavors (see section 3) are alternated between adjacent sections to
    create quiet visual rhythm without introducing new colors.
  - Pure white cards (SuiteCard-style) are reserved for content that needs to feel
    "light/approachable" (product catalog cards) vs. the dark violet cards which are
    reserved for "impact statement" content (pillars, security features, comparisons).


3. TYPOGRAPHY
----------------------------------------------------
Font: "Urbanist" (Google Fonts variable font, weights 300–900), fallback ui-sans-serif /
system-ui / sans-serif. Loaded once globally, applied via a CSS custom property
(--font-sans) rather than a Tailwind config file (Tailwind v4 CSS-first @theme).

Scale & usage patterns:
  - Hero H1:            44px → 58px → 60px (mobile → tablet → desktop), font-bold,
                         leading-[1.15], tracking tight (-0.5px mobile, -1.5px desktop).
  - Section H2 (every    text-3xl → text-4xl → 42px → 48px, font-bold,
    section uses this):  tracking-[-0.5px], leading-[1.15]. Always exactly two lines via
                         two <span class="block"> elements: line 1 neutral text color,
                         line 2 purple accent (#7A00C2).
  - Section supporting   text-lg → text-2xl, purple accent color (#7A00C2, same as the
    paragraph:           headline's second line — body copy under a headline is NOT
                         neutral gray, it continues the accent color at lower weight),
                         leading-relaxed.
  - Card headings:       text-xl to text-2xl, font-bold, white (on dark cards) or
                         near-black #16063A (on white cards).
  - Card body text:      text-sm to text-base, relaxed leading, ~90% opacity white on
                         dark cards (text-white/90) or slate/muted on white cards.
  - Micro-labels/badges: text-[10px] to text-xs, font-bold/font-extrabold, often
                         uppercase with letter-spacing (tracking-wide/tracking-[0.15em]).

Rule of thumb: headings are always font-bold or heavier, tracked slightly tighter than
default; never use a regular/light weight for a heading.

Punctuation & polish rules:
  - No trailing full stops. Strip the final period from the end of every text block —
    headings, subheadings, card/feature descriptions, taglines, ROI or metric values,
    footer lines, chatbot replies, helper captions. If a string in code currently ends
    in `.'` or `."`, remove that last period.
  - Keep INTERNAL periods that separate two independent clauses inside one longer
    flowing sentence (e.g. "Book a 30-minute briefing. We will show you exactly which
    suites map to your priorities" keeps its middle period — only the very last period
    of the whole block is dropped). Removing a mid-paragraph separator would merge two
    sentences into a confusing run-on, which is not the goal — the rule targets the
    trailing full stop, not internal grammar.
  - Compound two-line headlines (e.g. "Enterprise-Wide Outcomes. Nine AI Suites" /
    "Twenty-Seven AI Agents") follow the same logic: an internal period between two
    short clauses on the first line stays; the very last period at the end of the whole
    headline is dropped.
  - True ellipses ("...") are a different thing — a loading/continuation indicator (a
    terminal-style progress line, an input placeholder hinting at more text) — and are
    NOT affected by the no-full-stop rule. Don't strip them, and don't confuse a decimal
    point (e.g. a timestamp like "00:02.50", or a multiplier like "3.4x") with a
    sentence-ending period either — only touch a single period that is genuinely the
    last character of a sentence/phrase.
  - Metric/ROI values may cite a source in parentheses directly after the figure, name
    only, never a hyperlink — e.g. "40% Faster Sales Velocity (Gartner)",
    "70% reduction in data entry requirements (IBM & Deloitte)". The citation sits
    inside the same trailing-period-free string.


4. LAYOUT, SPACING, PLACEMENT & GAPS
----------------------------------------------------
Everything about where things sit and how far apart they are. Motion is deliberately
NOT in this section — see section 7, which is self-contained.

4.1 THE SHELL — one measure, every section
  `relative mx-auto w-full max-w-[1360px] px-5 md:px-8`
  One exported constant, imported by every section, page masthead, navbar and footer.
  20px inset on a phone, 32px from 768 up. Nothing on the page defines its own measure,
  which is what makes the hero headline's left edge land on the footer's left edge and
  every centred heading share one axis. Avoid nested max-widths — two containers drift
  apart on wide screens and the drift is invisible until someone screenshots it.

4.2 VERTICAL RHYTHM — four band sizes, chosen by weight not by habit
  py-12 md:py-16   48/64px   supporting bands (a pillars strip, a closing CTA card)
  py-14 md:py-16   56/64px   a single-card band
  py-16 md:py-24   64/96px   the standard content section (calculator, walkthrough)
  py-20 md:py-28   80/112px  a whole page's body (FAQ, a suite dossier)
  A band is sized by PADDING, never by min-height plus flex-centering: content-driven
  height means an extra line of copy grows the band instead of eating its air.

4.3 A FIXED NAVBAR CHANGES WHAT "BALANCED" MEANS ON THE BAND BELOW IT
  The bar is 72px tall, 84px from `md`, and it is `fixed`, so it sits OVER the first
  band rather than pushing it down. A page masthead therefore needs its top padding to
  carry the bar's height plus the gap it actually wants:
     pt-[112px] pb-10   = 72 + 40 above, 40 below   (mobile)
     md:pt-[132px] pb-12 = 84 + 48 above, 48 below  (desktop)
  Set the top padding to the same number as the bottom and the band reads top-heavy by
  exactly the height of the bar. This is the single most repeated spacing bug in a fixed
  -header layout.

4.4 THE 12-COLUMN GRID, AND THE GAP FLOOR THAT BREAKS IT
  Content rows are `grid grid-cols-12 gap-x-0 gap-y-8 lg:gap-x-10`, with children at
  `col-span-12 lg:col-span-5` / `lg:col-span-7` and similar.

  THE LAW: `repeat(12, minmax(0, 1fr))` lets every TRACK collapse to zero, but column
  GAPS never shrink. A 12-column grid therefore has a hard minimum width of 11 × gap.
  At `gap-x-10` that is 440px — wider than a 412px phone's 372px of shell — so the grid
  overflows by ~68px, every `col-span-12` child is laid out 440px wide, and the whole
  column's contents sit ~34px right of centre. `body { overflow-x: clip }` hides the
  scrollbar and the section simply looks mis-centred, which is why this is so hard to
  spot from a screenshot.

  THE RULE: a 12-column grid carries `gap-x-0` until the width at which its columns
  actually split, and only then takes its gap (`lg:gap-x-10`). A grid whose children
  split at every width may keep a gap, sized so that 11 × gap fits the narrowest shell
  — e.g. a `col-span-6` pair at `gap-x-4 sm:gap-x-8` (176px, comfortably inside 335px).

4.5 CENTRING SOMETHING BETWEEN TWO UNEQUAL FLANKS
  Applies to the navbar and to any row with a mark on one side and controls on the other.
  Three approaches, only one of which is correct:
    absolute left-1/2 -translate-x-1/2 — truly page-centred, but cannot be squeezed; when
      the flanks grow it paints the centre group straight over them.
    flex-1 on the middle — never overlaps, but centres the group in the space that is
      FREE, and free space is not symmetrical when one flank is 3× the other. The group
      lands visibly off the page's centre line.
    grid-cols-[1fr_auto_1fr] — CORRECT. The flanks are equal by construction whatever is
      inside them, the middle track is its own content, and it lands on the page's centre
      line. It participates in layout, so it holds content rather than overlapping.
  Flank items take `justify-self-start` / `justify-end`, since each track is now wider
  than its contents. Below the breakpoint the middle item is `display: none`, its track
  collapses to 0, and equal flanks reproduce `justify-between` exactly.

4.6 GROUPING BY GAP — the cluster rule
  Related controls are grouped by SPACING, not by rules and dividers. A row of three
  destinations that belong together sits at one small equal gap (10px, `gap-2.5`); a
  divider plus two 16px gaps between them reads as 33px of separation in the middle of
  the group, which makes one cluster look like two that drifted together.
  Corollary: a button in a dense bar is not the same object as a button at the end of a
  section. Bar pills run tighter (px-5 py-3 / px-4 py-3 at 13px) than page pills
  (px-6 py-3.5). Keep the VERTICAL padding identical across pills in one row so they
  stand at the same height; vary the horizontal by label length so a short label does not
  look padded beside a long one.

4.7 TWO COLUMNS THAT MUST START AND END TOGETHER
  Grid's default `items-stretch` gives the row's height to both columns; then
  `h-full` + `justify-between` on the list and `lg:h-full` on the panel makes the first
  item's top edge and the last item's bottom edge land on the panel's edges.
  `lg:h-full` has to be on the GRID ITEM (a wrapper counts), or an inner `h-full` is
  100% of a wrapper that already shrank to its content.
  Never solve this with `items-center`: two columns of unequal content sharing one centre
  line is not a structure, it is an average, and nothing lines up with anything.

4.8 HEADING BLOCKS
  - Centred over the section, `max-w-4xl` (the larger scale needs the room: a 27-char
    heading at 64px measures ~820px and a 3xl measure would wrap it).
  - Two scales only: clamp(30px, 4.8vw, 64px) for a section that opens a chapter, and
    clamp(27px, 3.9vw, 48px) for a supporting one. Scrolling out of a 64px heading into a
    48px one is what reads as a mismatch — copy leading and tracking across too, or the
    sizes will match while the line spacing does not.
  - mt-10 md:mt-12 from the heading block into the content row.
  - `text-wrap: balance` on every heading, plus a non-breaking space before the last word
    of a heading or tagline so a line can never end as a single orphan word.

4.9 PADDING & RADIUS SCALE (both move together — a small radius wants small padding)
  999px   pills, marks, chips
  6–10px  micro UI inside an illustrated window (buttons, fields, avatars)
  14px    an illustrated window itself
  16px    a list/step card                     px-4 py-4 sm:px-5 sm:py-6
  18–22px cards and panels                     px-6 py-10 md:px-12 md:py-11
  24–26px large containers and stage panels
  A radius above ~26px on a small element reads as a lozenge, and below ~14px on a large
  panel reads as a box: the two scales are not interchangeable.

4.10 GAPS INSIDE A COMPONENT
  gap-1 / gap-1.5   glyph to its own label (a badge, an inline icon)
  gap-2 / gap-2.5   controls in a cluster
  gap-3 / gap-4     a mark and the text block beside it
  gap-5 / gap-6     items in a list that are separate thoughts
  gap-x-10          two columns of a content row
  gap-y-8 / gap-y-16 stacked rows, larger when the rows are whole subjects

4.11 TEXTURE NEVER SITS BEHIND TEXT
  Every light band carries a dot grid. Any run of copy on top of one wears `.plate`: a
  `::before` at `inset: -28px -36px -22px -36px`, radius 48px, filled with the band's own
  base colour and pushed to `z-index: -1`. The result is a soft untextured field behind
  the words with no visible edge. Asymmetric insets on purpose — optical padding around a
  block of type is wider at the sides than above and below.

4.12 SMALL PLACEMENT RULES THAT KEEP EARNING THEIR PLACE
  - Balance the gap ABOVE a divider with the gap BELOW it. Don't assume two Tailwind
    steps (mt-5 into it, pt-4 out of it) are balanced — check the rendered pair.
  - Give a variable-length card footer a min-height sized for the WORST case, including
    its own top padding, so the divider above it lands at the same y across a row.
  - Numbered badges restart at 01 for each independent group; the reset is what says
    "separate set" rather than "continuation".
  - Elements read as one unit (icon + heading, label + value) stay on one row at every
    breakpoint.
  - Verify zero horizontal overflow at 320–414px after ANY layout change.


5. BACKGROUND TEXTURE SYSTEM (reusable utility classes)
----------------------------------------------------
Three interchangeable section-background "flavors," alternated down the page for quiet
depth. All three share the same technique: a base color/gradient, plus one or two
pseudo-element texture overlays (dot-grid and/or line-grid), with real content lifted
above the texture via z-index.

A) DARK HERO / CTA GRADIENT — .bg-ignitho-hero
   Used for: hero section, closing CTA banner, dark illustrative panels.
   background:
     radial-gradient(ellipse 95% 85% at 22% 18%, rgba(118,0,200,0.55) 0%, transparent 58%),
     linear-gradient(125deg, #16063A 0%, #2C0A78 28%, #4A12B8 52%, #123E68 86%, #0A5670 100%);
   ::before overlay: a faint 60px×60px white grid (two 1px linear-gradients at
   rgba(255,255,255,0.05)), pointer-events:none, absolutely positioned inset:0.
   Effect: a moody violet-to-teal diagonal glow with a barely-visible technical grid.

B) LIGHT TINTED SECTION — .bg-ignitho-light-grid
   Used for: sections that should feel soft/lavender-tinted (alternates with C below).
   background: linear-gradient(160deg, #F9F6FF 0%, #F0E8FF 50%, #F5F0FF 100%);
   ::before: 28px dot grid, radial-gradient dot at rgba(122,0,194,0.18).
   ::after: 56px line grid, two 1px linear-gradients at rgba(122,0,194,0.06).
   Children get position:relative + z-index:2 (`.bg-ignitho-light-grid > *`) so content
   always renders above the texture layers.

C) WHITE/NEAR-WHITE SECTION — .bg-ignitho-white-grid
   Used for: alternates with B for section-to-section rhythm without repeating color.
   background: solid #FBF9FF (a near-white, very slightly violet-tinted white — chosen
   deliberately over pure #FFFFFF so it doesn't feel stark against the tinted sections).
   Same dot-grid (::before, rgba(122,0,194,0.14)) and line-grid (::after,
   rgba(122,0,194,0.045)) overlays as B, just ~20% lower opacity since the base is
   already near-white.

Pattern: alternate B/C between adjacent content sections; reserve A for the very top
(hero) and very bottom (final CTA) of a page, i.e. as "bookend" high-impact moments.


6. COMPONENT PATTERNS
----------------------------------------------------
a) PRIMARY BUTTON (pill, teal):
   rounded-full, bg-ignitho-teal, border border-ignitho-teal-border, text white
   (#F9F6FE, an off-white not pure white), font-medium, px-6 py-3.5, hover: darker
   teal background + brighter border + pure white text. Icon (if present, e.g. an
   arrow) sits after the label with a small gap, and nudges further on hover
   (group-hover:translate-x-0.5).

b) SECONDARY BUTTON (pill, outline — used on dark backgrounds):
   rounded-full, border border-white/25, transparent fill, white text, hover: subtle
   bg-white/10. No border-color change on hover, just a fill wash.

c) DARK GRADIENT FEATURE CARD (Pillars / Security-style):
   rounded-[24px], padding ~24-28px, background: linear-gradient(160deg,#16063A 0%,
   #5B16C4 100%), border border-white/10, shadow shadow-[0_18px_46px_rgba(80,8,208,0.25)].
   Header row: heading (left) + icon badge (right) — icon badge is a small square
   (p-3, bg-white/10, border-white/15, rounded-xl) containing a plain white lucide
   icon. On hover: card lifts (-translate-y-1) and the icon badge scales up slightly
   and rotates a few degrees (group-hover:scale-[1.08] group-hover:rotate-6) — a
   signature micro-interaction used on every dark feature card.
   Body copy sits below, flex-1 so it fills remaining height; an optional footer
   (a metric/target line) is separated by a top hairline border (border-white/15).

d) TWO-TONE COMPARISON CARD (Problem/Fix-style — the "pricing card" pattern):
   Side-by-side pair, each rounded-[28px], solid saturated diagonal gradient fill
   (one card violet family #16063A→#5B16C4, the opposing card green-teal family
   #043620→#00A274), text always white. Decorative: two concentric large circles
   (border only, border-white/10) bleeding off the top-right corner, subtly scaling up
   on hover (group-hover:scale-110) for a "shine" effect.
   Header: icon + title INLINE on the same row (flex items-center gap-3) — not
   stacked — this is a deliberate, corrected choice (an earlier stacked-with-matching-
   left-edge layout was tried and replaced because icon+heading are meant to read as
   one unit on one line).
   Body: a vertical list of rows, each row = a small white circular icon badge
   (h-6 w-6, bg-white, icon colored in the card's accent hex, not pure black) + a
   line of white/90 text. Rows have a min-height so short/long text rows still line up.
   Whole card lifts and deepens its shadow on hover (hover:-translate-y-1.5 plus a
   larger shadow value) — the same restrained hover language as the dark feature card.

e) PRODUCT/CATALOG CARD (white, e.g. SuiteCard):
   White card, rounded-[26px], border-slate-200, soft shadow. Top third is an image
   with a dark violet gradient wash overlay (so any photo reads on-brand) plus a thin
   1px gradient accent bar along the very top edge (violet → teal, i.e. the brand
   gradient compressed into a single accent line) and a small pill badge + icon badge
   overlaid on the image. The white content area overlaps the image slightly
   (negative margin-top, -mt-6, with its own rounded-t corners) for a layered/stacked
   look. A callout box uses a colored left border (border-l-2) + tinted background
   (bg-violet-50) rather than a full colored fill — a lighter-touch way to highlight a
   key stat inside an otherwise white card. Card lifts on hover; the image scales up
   slightly (group-hover:scale-105) inside its overflow-hidden frame.

f) STAT CARD (simple metric card):
   Plain white, border-slate-200, rounded-2xl, centered text, a large bold number in
   the teal brand color (text-3xl/4xl font-black) above a small muted caption. No
   gradient, no icon — used when a grid of many small metrics needs to stay low-key.

g) FLOATING/OVERLAY UI (chat widget, modals):
   Dark near-black panel (#0A0620) with a soft accent-blue border tint, rounded-3xl,
   heavy shadow — visually distinct from the rest of the site (feels like a "console"),
   consistent with the accent-blue being reserved for "live/technical" moments.

h) BADGES / PILLS / CHIPS:
   Small rounded-full or rounded-lg elements, low-opacity tinted background matching
   whatever accent color is contextually relevant (e.g. bg-ignitho-teal/10 with
   text-ignitho-teal and a matching low-opacity border) — this "10% tint fill + full
   color text/border" formula is the standard way to make a small label feel branded
   without using a solid fill.


7. MOTION & ANIMATION SYSTEM
----------------------------------------------------
Self-contained on purpose: everything that MOVES lives in this section, and nothing in
section 4 depends on any of it. All of it is CSS — there is no animation library in the
build. JavaScript only ever toggles a class or sets a `key`; the browser owns the curve.

7.1 THE FOUR EASING TOKENS — every animation on the site uses one of these
  --ease-out        cubic-bezier(0.22, 1, 0.36, 1)    expo-out. Covers most of the
                    distance immediately, then settles. The default for reveals,
                    hovers and anything that should feel quick but not abrupt.
  --ease-mg         cubic-bezier(0.32, 0.72, 0, 1)    the Apple settle: a long, flat
                    tail with NO overshoot. Used where nothing may wobble — exits,
                    wipes, anything carrying type.
  --ease-mg-bounce  cubic-bezier(0.34, 1.28, 0.44, 1) the same curve with a small
                    overshoot past 1. 1.28 rather than the ~1.5 a tiny control could
                    take: a window full of text cannot wobble or the type doubles for
                    a frame. The smallest overshoot that is still felt.
  sheet curve       cubic-bezier(0.76, 0, 0.24, 1)    a symmetric in-out for a full
                    panel travelling a long distance (the mobile menu).
  Durations cluster in three bands: 0.2–0.36s for a state change, 0.6–0.9s for an
  entrance, 15–29s for ambient background loops. Nothing sits between 1s and 15s.

7.2 ENTRANCE — the reveal
  `.reveal` = opacity 0 + translate3d(0, 16px, 0) → none, 0.6s --ease-out on both.
  Driven by ONE shared IntersectionObserver (threshold 0, rootMargin 0 0 140px 0), so
  an element begins its entrance ~140px before it reaches the viewport and is already
  settled when it arrives. Fires ONCE — an entrance that replays on every scroll-past
  is a distraction and a permanent observer cost.
  Stagger with `transitionDelay` on the wrapper, index × 60–70ms, CAPPED at 200–240ms:
  uncapped, the ninth card in a grid waits 600ms and the reader has already read it.
  `.line-mask` is the heading variant: a clipping block whose inner span travels from
  110% to 0 over 0.9s, so a line rises out of nothing rather than fading.

7.3 THE MOTION-GRAPHICS FAMILY — blur-to-solid, used only inside the illustrated stage
  The signature: an element arrives slightly small, slightly low and BLURRED, then
  resolves. It reads as focus being pulled rather than as a slide.
  .mg        0.76s --ease-mg-bounce, `both`. Blur is animated to 0 by 45% of the
             timeline, deliberately BEFORE the overshoot — a blur still animating
             through an overshoot would be driven to a negative radius and clamp,
             which shows as a hitch.
  .mg-wipe   0.86s --ease-mg. The same arrival for something that reveals along an
             axis instead of scaling.
  .mg-out    0.36s --ease-mg. The exit, and it is the entrance played backwards
             (solid → blurred → gone) rather than a plain fade, so a panel leaves the
             way it came. The JS constant that keeps the outgoing panel mounted
             (EXIT_MS = 360) MUST equal this duration; if they drift, the panel either
             unmounts mid-animation or lingers.
  .stage-swap  0.78s bounce, scale 1.04 → 1 with a 5px blur clearing at 40%. The
             CONTENTS changing.
  .stage-pulse 0.66s bounce, scale 0.985 → 1, i.e. inward. The CONTAINER acknowledging
             that its contents changed. Two different jobs, so two animations.
  Stagger inside the stage runs ~120–160ms between sibling elements, which is what makes
  a panel read as one wave rolling through rather than five separate arrivals.
  TRICK WORTH KEEPING: to bounce a container that also holds cross-fading children,
  put the animation on a separate absolutely-positioned skin layer with a `key` tied to
  the current item. Changing the key remounts the skin and restarts its animation
  without touching the children's own transitions.

7.4 STATE METERS — animation as information, not decoration
  `.dwell-ring` is an SVG circle whose `stroke-dashoffset` runs from full to zero over
  `var(--dwell)` (5600ms), LINEAR — a countdown must not ease, or it lies about how much
  time is left. `stroke-dasharray` is 2πr computed for the exact radius (116.24 at
  r=18.5); a guessed value silently under- or over-fills.
  `.dwell-hold` pauses it with `animation-play-state: paused`, which holds the exact
  frame — which is why the JS timer behind it must BANK its remaining time rather than
  restart, or the drawn countdown and the real one diverge and the ring visibly lies.
  Restart-on-reselect is done with `key={turn}`, a counter bumped on every commit
  INCLUDING one that lands on the item already showing; a class toggle cannot restart a
  CSS animation, a remount can.
  The meter must not run while its section is off screen: gate it on the same
  IntersectionObserver flag as the timer, or a reader arriving a minute in finds a
  countdown that finished 55 seconds ago.

7.5 CONTROLS, DISCLOSURES AND OVERLAYS
  .disclose   grid-template-rows 0fr → 1fr, 0.34s --ease-out, with opacity at 0.24s.
              The one technique that opens to the content's OWN height — no max-height
              guess that clips a long answer or leaves a short one hanging.
  .row-fill   scaleY 0 → 1, 0.45s cubic-bezier(0, 0, 0.2, 1), transform-origin set from
              the edge the pointer crossed, so a fill grows from where you came in and
              retracts toward where you leave. BOTH states must be hand-written CSS:
              pairing Tailwind's `scale-y-0` (a six-function transform list) with a
              plain `transform: scaleY(1)` gives two states that cannot interpolate
              component-wise, and the fill snaps instead of growing.
              Drive it from a pointer-derived class, NOT `:hover` — the browser does not
              re-evaluate :hover while the page scrolls under a stationary cursor, so a
              hover-driven fill sticks on whichever row you were over before the scroll.
  .peek       0.5s scale+rotate entrance for a hover preview card; .peek-reel moves ONE
              transform (0.62s expo, cubic-bezier(0.16, 1, 0.3, 1)) across a pre-rendered
              tall reel, so changing rows mounts nothing and reloads no image.
  menu sheet  transform 0.66s cubic-bezier(0.76, 0, 0.24, 1), with `visibility` switched
              on `step-end` so the panel is not focusable during its exit.
  small pops  0.26–0.32s --ease-out `both` for chat bubbles and badges; the typing dots
              are a 1.1s loop staggered 0.14s apart.

7.6 AMBIENT BACKGROUND MOTION — the only thing that loops forever
  The dark aurora bands carry 5–6 overlapping gradient layers on 15s–29s
  `ease-in-out infinite alternate` loops (glow-breathe 16s, fold-a 15s, fold-b 19s,
  fold-c 25s, billow 29s, sheen 23s). Deliberately mutually prime-ish durations so the
  composite never visibly repeats. Nothing here moves fast enough to be noticed
  directly — it should read as light shifting, never as an animation.

7.7 WHAT DOES NOT MOVE — and this list is as load-bearing as the rest
  - BUTTONS. No slide, no scale, no ripple. A pill holds its position and shifts TONE
    on hover (0.2s ease) and dims to 0.82 opacity on press (0.12s). A hover state exists
    to confirm the control is under the pointer; moving it makes the eye track something
    that is not going anywhere. Both tones are one hue at two weights — a hover that
    arrives at a DIFFERENT brand colour reads as the button changing what it will do.
  - The navbar. It does not retract on scroll. A bar that comes and goes makes the reader
    check whether the navigation is there before reaching for it. The only thing that
    answers the scroll is its shadow: hairline at rest, soft shadow once the page has
    moved under it.
  - Type, at any point, for any reason other than an entrance. Transform-scaling rendered
    text softens glyph edges; where a "bigger when active" effect is wanted, prefer
    scaling the OTHER items down (0.975) so the one being read renders at 1:1.

7.8 INTERACTION RULES THAT PROTECT THE MOTION
  - Anything that auto-advances needs a real pause. Hover and focus are pointer and
    keyboard gestures; a touchscreen has neither, so an explicit pause/resume control is
    required (WCAG 2.2.2), and it must sit OUTSIDE any `aria-hidden` decoration.
  - Hold the clock on the ACTIVE item only. Hovering an inactive one should not stop it.
  - `:focus-visible`, never `:focus`, for a focus-driven hold: clicking a button focuses
    it and focus stays put, so a plain `onFocus` hold stops the timer permanently the
    first time anyone clicks. Browsers do not apply :focus-visible to pointer focus.
  - Clear hover state in the IntersectionObserver too: `pointerleave` does not reliably
    fire when the ELEMENT moves off a stationary pointer (i.e. on scroll), so a hold can
    survive the section leaving the screen with no event coming to release it.
  - Check `e.pointerType === 'mouse'` on pointerenter. It fires for touch as well, and a
    touch has no matching leave — that is the sticky-hover bug.
  - Wrap any :hover rule in `@media (hover: hover)`. A tap leaves a touchscreen element
    matching :hover until something else is tapped; guarding up front is one line, where
    undoing it afterwards is one rule per animated property.

7.9 PERFORMANCE — this system has to run on a cheap phone
  - `filter: blur()` costs a convolution over the painted area EVERY frame. Blur the
    smallest element that contains the content, never a wrapper — moving two blurs from
    a centring wrapper onto the inner block cut the blurred area by ~32% for an
    identical result.
  - No `will-change` on anything that repeats. It held a compositor layer permanently for
    ~25 buttons. The browser promotes a transform transition on its own, for its duration.
  - Gate scroll reads to one per animation frame, and gate every autoplay, entrance and
    meter on an IntersectionObserver — nothing animates while off screen.
  - `animation-fill-mode: both` plus `filter: none` in the final keyframe: leaving a
    non-none filter behind keeps a compositing layer alive after the animation ends.
  - Write `filter: none`, never `filter: blur(0px)` — minifiers rewrite the latter to
    `blur()`, which is invalid and drops the whole declaration.

7.10 REDUCED MOTION
  One stylesheet, imported LAST so it can override everything above it. Entrances are
  CANCELLED rather than shortened: shortening still fires a blur and a scale, which is
  exactly the class of movement the preference is about. Because the entrance animations
  use `fill-mode: both`, cancelling one strands the element at its `from` keyframe —
  blurred, offset and invisible — so the resting state must be restored explicitly
  (`opacity: 1; filter: none; transform: none`).
  Autoplay does not start at all under the preference, and the pause control is hidden
  with it: a button for something that is not happening is worse than no button.


8. RESPONSIVE DESIGN RULES (hard-won — corrected during development)
----------------------------------------------------
- Never use `hidden` on mobile for something that has no other way to be reached.
  (Concrete case: navigation links were originally `hidden md:flex` with literally no
  mobile alternative — links were unreachable. Fix: add a mobile hamburger trigger that
  reveals the same links in a stacked slide-down panel, keep desktop untouched.)
- Never use `hidden` on mobile for a meaningful visual element without a resized
  replacement. (Concrete case: a large decorative side-illustration was fully hidden
  below the desktop breakpoint. Fix: show a smaller, lower-opacity version of the same
  asset stacked below the text content on mobile, instead of removing it entirely.)
- Keep one consistent horizontal padding value per breakpoint across the whole page —
  don't let one section use `px-5` while a sibling uses a differently-nested container
  that produces a different effective inset; misaligned edges are very noticeable when
  scrolling.
- Absolutely-positioned floating elements that use only `right`/`bottom` (no `left`/
  `top`) can collapse to a shrink-to-fit width and wrap their text unexpectedly — pin
  them with an explicit anchor on all relevant sides or force `width:max-content` and
  `whitespace-nowrap` on the label.
- Elements meant to be read as one unit (an icon next to a heading, a label next to a
  value) should stay on one row (`flex items-center gap-x`) at every breakpoint rather
  than stacking, unless there is a deliberate, explicit reason to stack them.
- Verify zero horizontal scroll/overflow at small viewports (320–414px) after any
  layout change — this was used as the pass/fail check throughout development.
- Equal-height grids: rely on CSS Grid's default row-stretch behavior plus
  `flex h-full flex-col` on each card, not manually-set heights.


9. ICONOGRAPHY
----------------------------------------------------
Icon set: lucide-react (simple, consistent-stroke line icons). Icons are always either
pure white (on dark surfaces) or the section's single accent color (on light surfaces)
— never multi-color, never filled/solid style. Typical sizes: 14–16px inline within
badges, 20–28px as a standalone card-header icon. Stroke weight is occasionally bumped
above the default (stroke-[2.5] to stroke-[3]) specifically for small icons (≤16px)
sitting inside a tight badge, so they don't look too thin at small sizes.


10. QUICK-REFERENCE CHECKLIST FOR REPLICATING THIS SYSTEM ELSEWHERE
----------------------------------------------------
[ ] Load Urbanist (or a similar humanist grotesque variable font), weights 300-900.
[ ] Set up the 3-part color system: one teal action color, one violet/purple depth
    family (5-6 stops from near-black to bright violet), one green-teal "positive"
    gradient family, plus near-black text and muted gray captions.
[ ] Build the two-tone headline pattern (neutral line 1 / accent-purple line 2) and the
    accent-purple supporting paragraph as a reusable heading block.
[ ] Build the 3 background-texture utility classes (dark hero gradient+grid, light
    tinted+dot-grid, white+dot-grid) and alternate the two light ones between sections.
[ ] Build one pill-button component (teal solid + white/outline variants).
[ ] Build one dark-gradient-card component with the icon-badge-hover-rotate detail.
[ ] Build the two-tone comparison-card pattern for any "before/after" or "us vs them"
    content instead of a table.
[ ] Apply the single hover formula (lift + shadow + 300ms ease-out) to every card type,
    and keep BUTTONS out of it — they change tone only, and never move (7.7).
[ ] Set up the four easing tokens (7.1) before writing a single animation, so nothing
    invents its own curve.
[ ] Give every 12-column grid `gap-x-0` until its columns actually split (4.4), and
    centre anything between unequal flanks with `1fr auto 1fr` rather than flex-1 (4.5).
[ ] Pad the first band under a fixed header by the header's height PLUS the gap it
    wants, or it reads top-heavy by exactly that height (4.3).
[ ] Audit every section at 320-414px width: nothing is `hidden` without a replacement,
    no horizontal scroll, icon+label pairs stay inline, paddings match across sections.
[ ] Strip every trailing full stop from copy (headings, cards, ROI/metric values,
    footers, chatbot text) — keep only internal sentence-separator periods and true
    ellipses; never touch decimal points or multipliers (e.g. "3.4x").
[ ] Size hero/band sections by padding (content-driven height), not a fixed min-height —
    check the gap above and below the text reads as deliberate, not oversized.
[ ] On any card with a divider line, compare the gap above it to the gap below it — they
    should read as balanced, not top-heavy — and give variable-length footer text a
    min-height so dividers align across a card row regardless of line-wrap differences.
